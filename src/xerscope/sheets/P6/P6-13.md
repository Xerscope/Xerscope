# P6-13 · BEI

Baseline Execution Index: completed activities against the baseline's activities.

## Population (denominator)
Every activity of the baseline, except milestones (`TT_Mile`, `TT_FinMile`) and level of
effort (`TT_LOE`), whatever its baseline finish. Needs a baseline (sidebar).

## Counted (numerator)
Activities of the current update that are complete (`TASK.status_code` = `TK_Complete`),
same exclusions. A completed activity counts even if it was not due yet, so the counted set
is not a part of the denominator's set.

The list shows the activities due by the data date in the baseline and not complete.

Value = counted / denominator (ratio). Target `> 0.95`, as report R1 shows it; the
[EPPM dialog help (91574)](https://docs.oracle.com/cd/G18294_01/p6help/en/91574.htm) says 0.95 or
greater, so exactly 0.95 passes in EPPM and fails here.

## Source
- [P6 Professional help (101248)](https://docs.oracle.com/cd/G18296_01/client_help/en_US/101248.htm)
  and [P6 EPPM help, BEI section (46277)](https://docs.oracle.com/cd/G18294_01/p6help/en/46277.htm):
  denominator = baseline activities finishing before the data date.
- A P6 Professional report (R1, `docs/standards.md`) divides by every baseline activity;
  xerscope follows the report. The [Ten Six article](https://tensix.com/using-the-p6-check-schedule-tool/)
  reports a wrong BEI in P6 Professional r22.12 (1.0 where EPPM gives about 0.55).
- Same check in DCMA-14 with the help's reading (due by the data date).

## Example
Baseline: A100–A130, all four task-dependent. Update: A100 and A110 complete, A130 complete
early.

3 counted / 4 baseline activities = 0.75: fails. With the help's reading, if only
A100–A120 were due: 3 / 3 = 1.00.

## Change it
Target: `target` of `P6-13` in `standards/p6.toml`. The help's reading (due activities only):
the rule `bei` with `due_from = "baseline"` in your own standard.
